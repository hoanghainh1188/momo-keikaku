## Intent

**Problem:** `apps/worker` is an empty skeleton and there is no job runner. The database has exactly one role — `momo`, a superuser — so the separation the architecture depends on does not exist: pg-boss installs and migrates its own schema on `start()`, which is DDL that a non-owner application role must not be able to perform.

**Approach:** Split the roles, and move the DDL to the one that owns it. A `migrator` role installs and migrates the `pgboss` schema from the SQL pg-boss generates; the worker connects as a restricted `app` role with `migrate` and `createSchema` off, holding only DML on that schema. The worker boots, proves it can enqueue and consume a job as the restricted role, and shuts down cleanly.

## Boundaries & Constraints

**Always:**
- `pg-boss` at the decided `12.33.2`, exact.
- The `app` role must **fail** if it tries DDL on `pgboss`. That is the property this slice exists to establish, so prove it with a probe rather than asserting it.
- The migrator path uses pg-boss's own generated SQL — `getConstructionPlans(schema, opts)` and `getMigrationPlans(schema, version, opts)` — never hand-written DDL that could drift from the library's expectations.
- Configuration comes through `packages/app/src/config.ts`. Any new key is added to that schema, never read from the environment elsewhere; the clock/env fence makes a second reader a lint error.
- All six existing gates stay green: lint, three typechecks, and 53 tests across 4 files.

**Never:**
- **The `app` role does not take over the existing connection.** Its table grants are generated by story 1.2's table-class registry and do not exist yet, so pointing web, seed, scripts or the tests at it would leave them with no access to any application table. `DATABASE_URL` keeps naming the existing role; the new role is used for `pgboss` only.
- **No table-class registry, no `rls.sql`, no `grants.sql`, no triggers.** All story 1.2's.
- **No job handlers, no schedules, no ingest.** Those arrive with the Connector in Epic 5. This slice proves the runner works, not what it runs.
- **No `pnpm dev` orchestration** — slice B3, blocked on 1.2 and 2.1.
- No schema change to application tables, no migration, no seed data touched.

- **The spike the architecture asked for is already done; do not repeat it.** pg-boss 12.33.2's `MaintenanceOptions` carries `migrate?: boolean` and `createSchema?: boolean`, and the package exports `getConstructionPlans(schema?, options?): string`, `getMigrationPlans(schema?, version?, options?): string` and `getRollbackPlans(...)`. So the split is directly supported: migrator executes the plan SQL, app constructs with both flags false. Confirm the exact call shapes against the installed `dist/types.d.ts` rather than from memory.
- `infra/docker-compose.yml` — one role today (`POSTGRES_USER: momo`, superuser) on host port **55433**. Roles must be created somewhere that runs before the worker; compose's `docker-entrypoint-initdb.d` runs **only on an empty volume**, and the volume here is already initialised, so an init script alone will not take effect on existing machines or on the CI service. Prefer an idempotent SQL step the migrator path runs every time.
- `packages/db/src/client.ts` — `DATABASE_URL` with a hardcoded fallback, one sanctioned `process.env` disable. Leave both; the fallback is recorded in `deferred-work.md` as story 1.2's.
- `packages/app/src/config.ts` — the only env reader. New keys for the migrator and app connection strings belong here, and the fail-boot behaviour should name them the way `DATABASE_URL` is named.
- `apps/worker/src/index.ts` — `export {}` today, with a comment naming this slice. It has its own `tsconfig.json` and a `typecheck` script gated in CI.
- `.github/workflows/ci.yml` — six gates, a `postgres:18.6-alpine` service, and a `Prepare database (schema + seed)` step that runs `drizzle-kit push` then `pnpm seed`. Role creation and the pgboss install belong in that prepare path so the worker probe has something to connect to.
- `eslint.config.js` — the clock/env fence covers `apps/**` and `packages/**` across eight extensions. Worker code is inside it: reading `process.env` or the wall clock there is an error.
- `packages/db/src/db-round-trip.test.ts` — the pattern for a database-backed test: `REQUIRE_DB=1` turns an unreachable database into a failure rather than a skip, so CI cannot pass by not running it. A worker test should follow it.

## Implementation Notes

**Where each piece landed.**

- `scripts/pgboss-migrate.ts` (new, `pnpm pgboss:migrate`) is the migrator step. It lives in
  `scripts/` rather than under `packages/` for two reasons: it is a migration step run beside
  `drizzle-kit push` and `pnpm seed`, and `scripts/` is deliberately outside the clock/env
  fence. It still takes configuration from `packages/app/src/config.ts` rather than reading
  the environment itself, so a missing key fails there naming the key.
- `apps/worker/src/boss.ts` (new) holds `createBoss(connectionString)`; `apps/worker/src/index.ts`
  is only the composition root (config → runner → start → signal shutdown). The split exists so
  the test can build the same runner without starting a process's signal handlers.
- `apps/worker/src/worker-round-trip.test.ts` (new) carries both the job round trip and the
  restriction probe, so the property is gated rather than hand-checked.

**Decisions taken inside the spec's boundaries.**

- *One new config key, not two.* `APP_DATABASE_URL`. The migrator reads the role name and
  password out of that same string, so the role the worker connects as and the role the
  migrator creates cannot disagree — a name key and a password key could. `DATABASE_URL` is
  untouched and still names the existing role, as the spec's Never requires.
- *`momo_migrator` is NOLOGIN.* Ownership is the property that matters, not a second login.
  The step assumes it with `SET ROLE` from the owning connection, so the DDL runs as the
  migrator and every object belongs to it — with no second credential to manage and no second
  config key. Verified: `\dn+` reports `pgboss` owned by `momo_migrator`.
- *Two more constructor flags beyond the two the spec names.* `reindex: false`, because
  maintenance rebuilds bloated job indexes with `REINDEX INDEX CONCURRENTLY` and only an
  index's owner may run that — pg-boss's own types document this exact case. And
  `schedule: false`, because the spec's Never excludes schedules and the timekeeper would
  otherwise create an internal queue and poll for cron work that cannot arrive. Supervision
  stays ON: expiry, retries and retention are DML, which the app role holds.
- *Grants are re-issued on every run* rather than left as `ALTER DEFAULT PRIVILEGES` state in
  the catalog, so objects a future pg-boss migration adds are covered by the next run of the
  same step. `EXECUTE` on the schema's functions is not granted: PostgreSQL grants it to PUBLIC
  already, and `pgboss.create_queue` is SECURITY INVOKER — so the one branch inside it that
  performs DDL (a partitioned queue) is still refused for the app role.
- *The migration path splits at the plan's own `COMMIT;`.* `getMigrationPlans` appends inlined
  `CREATE INDEX CONCURRENTLY` statements after the COMMIT, and those cannot run inside the
  implicit transaction a multi-statement simple query would put them in. pg-boss says to use
  `migrateCommands()` for this, and `migrateCommands` is not exported; splitting at the COMMIT
  gets the same effect from the exported surface. The tail is empty for every migration in
  12.33.2 (checked for v40→42), so this is insurance against a future upgrade, not a path
  exercised today.
- *The target schema version is read from `pg-boss/package.json`'s `pgboss.schema`* — the same
  field `dist/contractor.js` reads. Hardcoding 42 would leave a pg-boss upgrade silently one
  version behind, which the worker then refuses to start against.

**Things the spec did not predict.**

- `vitest.config.ts` had to grow `apps/**/*.test.ts`; its `include` was `packages/**` only, so
  a worker test would never have been collected. A test the runner does not collect is not a
  gate.
- `pg-boss` is declared in two manifests — the root (the migrator script) and `apps/worker`
  (the runner). Each is a genuine consumer, but it adds a fourth name to the exact-pin lockstep
  problem deferred-work.md already records for `drizzle-orm`/`pg`.
- `apps/worker/package.json` gained a `start` script (`tsx src/index.ts`), which is how the
  worker is run by hand. This is not `pnpm dev` orchestration — that is slice B3.
