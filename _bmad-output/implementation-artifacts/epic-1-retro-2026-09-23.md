### Behaviour — the defect the per-story gates could not see

#### F1 — The test suite does not pass against a real database on a developer machine, and the failure set changes every run — HIGH — *fix now*

**Claim.** From a freshly created database, `pnpm test` fails, and it fails differently each
time. This is not a stale-state artifact: the database was destroyed and rebuilt before each run.

**Evidence** (this retrospective, 2026-09-23, macOS, Postgres 18.6 via `infra/docker-compose.yml`,
the exact CI prepare sequence from `.github/workflows/ci.yml:388–397`):

| Run | Setup | Result |
|---|---|---|
| Pristine 1 | `down -v` → up → push → pgboss → policies → seed | **2 failed** / 982 passed — `seed-load-orchestration`, `org-writes` (`audit_log_pkey` duplicate) |
| Pristine 2 | identical | **1 failed** / 983 passed — `seed-load-orchestration` |
| Pristine 3 | identical | **many failed** — `google-sign-in`, `identity`, `password-reset`, `cross-tenant` (4 cases), `seed-load-orchestration` |
| `seed-load-orchestration.test.ts` **alone**, pristine | identical | **1 passed** — green |

The file that fails in every run passes when it is the only file running. That isolates the cause
to concurrency between test files, not to the code under test.

**Mechanism, with sources.** Vitest runs test files in parallel worker threads and
`vitest.config.ts` sets no `fileParallelism`, `poolOptions.threads.singleThread` or `sequence`
control (`vitest.config.ts:36–50` — the `test` block carries only `include`, `environment` and
`env`). Every database-touching suite therefore shares one Postgres database concurrently. Two
mechanisms built by different stories then collide:

- Story 1.2 built the probe-tenant harness: many suites create `xtprobe-*` Tenants concurrently,
  partitioned by disjoint id ranges (`packages/db/src/probe-tenants.ts`, `assertProbeTenantsDisjoint`).
- Story 1.8 added `assertSingleTenantDatabase` (`packages/db/src/seed.ts:678–691`), which counts
  **every** row in `tenant` and refuses when more than one exists. It cannot distinguish a
  *leftover* probe from a *live* probe belonging to a suite running right now. Its own comment
  names the case it means to catch — "leftover probes beside the demo" — which is precisely the
  distinction it cannot make.
- The advisory lock that was meant to serialise this covers only the two seed suites against each
  other: `SEED_SUITE_LOCK = 8_700_000_018` is taken in `tests/seed-load-orchestration.test.ts:33,40`
  and `tests/seed-fixture-clock.test.ts:30,53` — a repo-wide grep finds `pg_advisory_lock` in
  those two files and nowhere else. No probe-creating suite takes it.

The observed failure text states the collision directly:
`Refusing to seed: this database holds 3 Tenants — ten-momo, xtprobe-a-000591, xtprobe-rates-000591`.

The `audit_log_pkey` duplicate-key failures and the `40P01` deadlock on the 24-table
`TRUNCATE … CASCADE` are the same root cause seen from the other side: the seed truncates every
registered table and calls `syncIdentitySequences` (`packages/db/src/seed.ts:721–731`,
`setval(…, MAX(seq))`) while other suites hold rows and sequence values in flight.

**Why no story could have caught it.** Each story's gate ran green in isolation, and this is a
*cross-suite* race — story 1.8 added a guard that is correct for an operator at a terminal and
wrong for a parallel test runner, against a harness story 1.2 had built six stories earlier.
Neither session saw both sides. This is exactly the class the retrospective exists to find.

**Why CI is green and this matters anyway.** `gh run list` shows `main` green through PR #43,
so the Linux runner currently wins the race. That does not make the defect benign:
1. The local feedback loop is broken — a developer on this machine cannot get a trustworthy
   `pnpm test`, and will learn to ignore red.
2. The CI pass is timing, not design. Nothing in the code prevents the same interleaving on the
   runner.
3. `HANDOFF.md:395–398` records that branch protection is **off** and the nine gates "report and
   do not block". A flaky suite plus non-blocking gates means a genuine regression can merge
   while looking like a known flake.

**Proposed fix (not applied).** Two options, and the smaller one is the weaker one:
1. Exclude probe ids from `assertSingleTenantDatabase`'s count. Smaller, but the `xtprobe-`
   prefix is a convention each test file passes into `buildProbeTenant(...)` by hand
   (`tests/seed-load-orchestration.test.ts:28`), not something `probe-tenants.ts` enforces — so
   the guard would depend on a naming habit.
2. Have the probe-tenant harness take `SEED_SUITE_LOCK` in shared mode while the seed takes it
   exclusively. Larger, but it is the only option that also removes the `TRUNCATE` deadlock, and
   it does not rest on a naming convention.

Option 2 is the one this retrospective recommends. Either way, add a regression test that runs the
suite against a database that already holds a probe Tenant.

### Story-boundary defects (adversarial / edge-case / verification-gap lenses)

#### F18 — The currency lock's check and its write are two untransacted round-trips — MEDIUM — *fix now*

**Claim.** `changeTenantCurrency` reads whether any Rate exists in one transaction and writes the
currency in a separate, untransacted statement, with no lock and no re-check. The "currency cannot
change once any Rate exists" invariant is therefore not enforced atomically.

**Evidence, re-verified against the primary source for this retrospective.**
- `packages/app/src/use-cases/tenant-currency.ts:35–39` — `if (await deps.hasAnyRate(ctx.tenantId))
  { return fail(...) }` then `await deps.setCurrency(...)`, two separate awaits.
- `packages/db/src/repo-tenant-currency.ts:13–28` — `hasAnyRate` opens its own
  `withTenant(handle, tenantId, …)` transaction; `setCurrency` is a bare `handle.update(tenant)`
  outside any transaction.

**Failure scenario.** A Tenant has zero Rates. An Admin calls `changeTenantCurrency`; `hasAnyRate`
returns `false`. Before `setCurrency` runs, a concurrent `createProject` commits — it dual-writes
a `project_default_rate_entry` at yen 0 (`packages/app/src/use-cases/org-writes.ts:246–255`). The
currency write then commits anyway, on a Tenant that now has a Rate.

**Seam.** Story 1.6 (Rates) meets story 1.9 (the currency lock), three stories apart.

**Current blast radius.** Unobservable in R0: the only accepted currency is JPY, so the write is
JPY→JPY. It becomes real the day a second currency is accepted. Already recorded at
`deferred-work.md:928–930` and `spec-1-9-….md:141`; re-verified here rather than taken on trust.

**Negative evidence — checked and clean.** Every other check-then-write in the audited-write
surface re-verifies its precondition against freshly locked rows inside the same transaction that
performs the write: `org-writes.ts`'s `visibleDepartment` / `visibleProgram` / `visibleProject`
take `.for('update')` row locks, and `membership-writes.ts`'s `lockCallerAndTarget`
(`packages/db/src/repo-membership-write.ts:67–93`) takes one ordered `SELECT … FOR UPDATE` before
any decision. `tenant-currency.ts` is the **only** instance of this shape, not one of a family.
That is what makes it cheap to fix.

#### F19 — The identity-sequence resync is correct only because the seeding role is a superuser — LOW — *defer, with a tripwire*

**Claim.** `syncIdentitySequences` computes `SELECT MAX(seq)` inside the just-written Tenant's own
`withTenant` transaction (`packages/db/src/seed.ts:503–506`, `:708–731`). It is correct across
coexisting Tenants only because the seeding connection bypasses `FORCE ROW LEVEL SECURITY` as a
Postgres superuser. If it were scoped by RLS, `MAX(seq)` would see one Tenant's rows only and
`setval(…, X, true)` would drive a *shared* identity sequence backwards below a value another
coexisting Tenant already used.

**Why it matters later, not now.** `packages/db/src/probe-tenants.ts:377–382` deliberately keeps
several Tenants coexisting and calls the resync once per probe. `assertProbeTenantsDisjoint`
(`:324–368`) checks only that the `seq` bands do not overlap — never that they are written in
increasing order. Making the migrator/seed connection a non-superuser is an already-open item
(`deferred-work.md:157–159`). Closing that item **without** revisiting this resync would turn a
latent coupling into primary-key collisions.

**Relation to F1.** Distinct mechanisms sharing a root: both are cases where the seed reasons
about a global sequence or a global Tenant count while other suites hold state concurrently.
Confidence: medium — the coupling is verified by reading; the triggering interleaving was not
reproduced.

#### F24 — The comparator the criterion names is unused, and the one that ships returns "equal" for distinct strings — MEDIUM — *fix now*

**Criterion** (`epics.md:744`): text "sorts by Unicode code point **after NFKC width
normalisation** through the single `domain/text.compareNfkc`".

**As-built.** `compareNfkc` (`packages/domain/src/text/compareNfkc.ts:5–11`) is correct and has

**Measured this session** — `sensitivity: 'base'` reports these *distinct* strings as equal, while

| Pair | NFKC-equal? | `compareNfkc` | shipped `localeCompare(base)` |
|---|---|---|---|
| `あ` vs `ア` (hiragana / katakana) | no | −1 | **0** |
| `ガ` vs `カ` (dakuten) | no | +1 | **0** |

story 2.3 is literally *"One canonical order for everything the scheduler reports"*. Two WBS labels
differing only by kana type, case or dakuten would order non-deterministically today.

*(This is an upgrade on the sub-agent's finding, which reported only that `compareNfkc` was
unused. The instability was measured here.)*
