## Intent

**Problem:** Appends to append-only (watermarked) tables allocate `seq` with no lock. `mapping_event` takes `MAX(seq)+1` from a SECURITY DEFINER allocator, so two concurrent writers — in any Project or Tenant — read the same value and the loser fails with `mapping_event_pkey` 23505; this makes the full `pnpm test` flaky (2 of 17 runs). Without the lock, a lower `seq` can also commit after a higher one, so a reader pinning "latest row at or below `seq`" can miss rows (AD-20, AR-37).

**Approach:** One `packages/db` helper takes `pg_advisory_xact_lock(namespace, key)` (two-argument form; namespace 1 = Project, 2 = Tenant; `key` derived by the application from the identifiers) inside the caller's `withTenant` transaction, before the first append of that transaction. Every production append to a watermarked table goes through it. A shared variant exists for the future `ComputationInputs` capture. A CI concurrency test proves serialisation.

## Boundaries & Constraints

**Always:**
- The lock is transaction-scoped (`_xact_`), issued on the scope's `tx`, with **bound** int4 parameters — never interpolated.
- The key derivation is the application's and is documented in one place: first 4 bytes of SHA-256 over `tenantId + '\0' + scopeId`, read as a signed int32. A collision only over-serialises; it never breaks correctness.
- Lock order: Project key before Tenant key when one transaction needs both. Nothing takes a Tenant key and then a Project key.
- Long work happens before the lock; the lock is the last thing before the first append.
- Two-argument locks live apart from the one-argument bigint key `8_700_000_018/19` used by `seed-suite-lock.ts`; that lock is not touched.

**Never:**
- No `ComputationInputs` capture is built here (Review/export/publish are later epics); only the shared-lock helper and its test.
- No single-argument `hashtext` form (the spine withdrew it).
- No change to `identity_event` (global, no Tenant or Project to key on), the seed's band scheme, or `seed-suite-lock.ts`.
- No Epic 2/5 writers (2.9, 2.10, 5.5) — they will call the helper when they land.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Same Project, concurrent | Two map dispositions on one Project at once | Second waits; both commit; `seq` order equals commit order | N/A |
| Different Projects, concurrent | Two map dispositions on two Projects (either Tenant) | Neither waits on the other; no 23505 | N/A |
| Shared vs exclusive | Shared lock held on a Project key; an append starts | Append waits until the shared holder commits | N/A |
| Rolled-back write | Append tx rolls back | Lock released; next writer proceeds | Error propagates unchanged |

## Decisions (founder, 2026-09-23)

- **D1 — `seq` becomes an identity column (1-A).** Migration `0001` adds `GENERATED BY DEFAULT AS IDENTITY` to `mapping_event.seq` and `actuals_ledger_entry.seq` (expand-only; the identity counter starts past the current `MAX(seq)`). The seed writes both with `OVERRIDING SYSTEM VALUE` and both join `IDENTITY_SEQ_TABLES`; `clientAllocatedSeq` and the two `momo_next_*_seq()` allocators are removed from the registry, generator and checked-in SQL. A database that already has the functions keeps them harmlessly until a later contract step drops them.
- **D2 — every production append to an append-only table locks (2-A).** Project key: `mapping_event`, `disposition_event`, `project_default_rate_entry`. Tenant key: `rate_entry`. `audit_log` rides on the key the transaction already holds; when it holds none, the sink takes the Tenant key. Story 1.2 closes with this slice.
- **D3 — the spec stays whole (~1,650 tokens), not split.**

## Implementation Notes

- Held keys are remembered per transaction in a `WeakMap` keyed by the scope's `tx`; a repeat request issues nothing, and a Project key requested after the Tenant key throws (lock order). The audit sink calls `holdsWatermark(tx)` and takes the Tenant key only when no exclusive key is held. `auditSinkOn` now takes the `Bound`.
- Tenant scope key: `scopeId` is the Tenant's own id, so the key is SHA-256 over `tenantId + '\0' + tenantId`.
- `repo-resource.ts` `findProject` moved from `FOR UPDATE` to `FOR NO KEY UPDATE`: holding `FOR UPDATE` on the Project row while waiting for the Project watermark lock deadlocks against a Mapping append that holds the lock and needs `FOR KEY SHARE` on the same row for its FK. `FOR NO KEY UPDATE` still serialises against a rename.
- Migration 0001 is drizzle-kit output plus one hand edit: two DO blocks that start each identity counter at `MAX(seq)+1`, lifting FORCE RLS for that one statement (the owner is subject to FORCE) and restoring it. Verified on an upgraded database (rows at 5000/7000 → next values 5001/7001, FORCE still set).
- CI's drift-step error text no longer says "keep it one file, 0000".

## Design Notes

Why commit order matters: a reader pins `seq_max` under the shared lock. Because every writer must hold the exclusive lock *before* it obtains a `seq`, no transaction can hold an uncommitted `seq` below the pin once the shared lock is granted.

```ts
await lockWatermark(bound, { kind: 'project', projectId });
await tx.insert(s.mappingEvent).values(rows); // seq from identity, after the lock
```
